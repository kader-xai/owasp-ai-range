LLM02:2025 · Synthetic records only

Sensitive information disclosure

The problem

You are Alice, asking a support assistant about your ticket. The vulnerable application retrieves Alice’s and Bob’s records together. Bob has a fictional private reference that Alice must not receive.

How the attack works

Ask for information from another customer’s record. If the model reveals it, sensitive information crosses an access boundary. Prompt injection can help cause disclosure, but LLM02 describes the leaked information; LLM01 describes instruction manipulation.

The ball analogy

Records are balls passed to the LLM. If Bob’s private ball enters Alice’s lane, the LLM can pass it back to Alice. The application must sort the balls before they reach the model.

Vulnerable: both customers’ records enter the model context.

The defense

The server fixes the demo identity to Alice and filters records by ownership before inference. Changing an identity field in a replay does not grant access. This demo identity is not real login or production authentication.

We test a fictional reference, not real passwords or personal data. A missing reference in one answer does not prove security. Filtering protects this retrieval path, not every possible leak.
