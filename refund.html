When a customer attachment becomes policy.

Submit a customer document to a refund assistant. Inspect the model proposal and the quote actually saved by the business application.

Approved server policy: 30 days. A customer attachment cannot authorize a different policy. No money moves; every quote is a synthetic local database record.
Learning brief and architecture

Workspace → saved attachment revision → approved policy + untrusted attachment → model proposal → application policy gate → quote and attempt committed together.

Ball analogy: an instruction printed on the customer’s ball tries to steer the assistant toward a different quote. The defended application checks the landing zone before storing the result. The model can still make an unsafe proposal; application enforcement limits its effect.

Both variants use the same context and schema. Vulnerable mode trusts a well-formed model proposal; defended mode independently compares its value to the server policy. Schema validity is not authorization. Failed attacks are recorded as failures, not converted into simulated wins.

Context preview is not inference. Select Ollama for a real attack attempt. This tests a narrow policy decision, not a universal injection defense or real refund service.
